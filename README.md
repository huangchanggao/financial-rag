# Financial RAG — SEC 10-K Analysis SystemA multi-company Retrieval-Augmented Generation (RAG) system for analyzing SEC 10-K filings.The system combines structured SEC filing parsing, SQLite metadata management, LLM-based section routing, FAISS retrieval, and Cross-Encoder reranking to answer questions using retrieved filing evidence.---## OverviewLarge SEC 10-K filings contain many different sections and hundreds of text chunks. Performing semantic search over the entire document can retrieve content from the wrong section, especially when similar terms appear in different contexts.This project uses a hierarchical retrieval workflow:1. Identify the company from the user's question.2. Load the company's available 10-K sections from SQLite.3. Use an LLM to select the section most likely to contain the answer.4. Search for relevant chunks only inside the selected company and section.5. Rerank retrieved chunks using a Cross-Encoder.6. Send the highest-ranked evidence to the LLM for grounded answer generation.The current dataset includes:- NVIDIA (`NVDA`)- Advanced Micro Devices (`AMD`)- Microsoft (`MSFT`)---## Current Architecture```textUser Question      |      vCompany / Ticker Router      |      vSQLite Section Metadata      |      vLLM Section Selector      |      vSelected SEC 10-K Section      |      vFAISS Chunk Retrieval      |      vCross-Encoder Reranking      |      vTop-K Evidence      |      vGrounded LLM Answer```### ExampleQuestion:```textWhat market risks does AMD discuss?```The system may route the query as:```textAMD  ↓Item 7A  ↓FAISS candidate retrieval  ↓Cross-Encoder reranking  ↓Top 5 evidence chunks  ↓Grounded answer```---## Features### Multi-company SEC ingestionThe ingestion pipeline supports multiple companies and stores company, filing, and chunk metadata in SQLite.Current companies:```textNVDAAMDMSFT```### SEC 10-K section parsingThe parser detects standard 10-K sections such as:```textItem 1Item 1AItem 1CItem 7Item 7AItem 8...```Section identifiers and section titles are stored separately.Example:```textsection: Item 1Atitle: RISK FACTORS```### Section-aware chunkingEach extracted section is split into overlapping text chunks while preserving metadata including:```texttickerfiling datesectionsection titlechunk index```### SQLite metadata storageThe project uses three primary tables:```textcompaniesfilingschunks```This separates company-level, filing-level, and chunk-level information while preserving their relationships through foreign keys.### LLM Section SelectionInstead of searching all chunks immediately, the system first provides the available section metadata for the detected company to an LLM.The LLM selects one section that is most likely to contain the information required by the question.Example:```textQuestion:What are AMD's main risk factors?Selected section:Item 1A```### FAISS RetrievalAfter section selection, FAISS performs semantic retrieval only within:```textselected company+selected section```This reduces irrelevant cross-company and cross-section retrieval.Embedding model:```textsentence-transformers/all-MiniLM-L6-v2```### Cross-Encoder RerankingFAISS is used as the candidate-generation stage.Retrieved candidates are then reranked with:```textcross-encoder/ms-marco-MiniLM-L-6-v2```Unlike embedding similarity, the Cross-Encoder evaluates the question and each candidate chunk together.The final highest-ranked chunks are used as evidence for answer generation.### Grounded Answer GenerationThe answer model is instructed to:- use only retrieved SEC filing context;- avoid unsupported claims;- state when retrieved evidence is insufficient;- cite the retrieved filing sources.Current LLM:```textopenai/gpt-oss-20b```via Groq.---## Data Pipeline```textSEC EDGAR    |    vDownload 10-K HTML    |    vHTML Cleaning    |    vSection Detection    |    vSection-aware Chunking    |    vSQLite    |    vFAISS Vector Index```---## Database Structure### companiesStores InstallationCreate and activate an environment:```bashconda create -n financial-rag python=3.11conda activate financial-rag```Install dependencies:```bashpip install -r requirements.txt```Create a `.env` file based on:```text.env.example```and provide the required API credentials.---## Running the Pipeline### 1. Initialize the database```bashpython src/database.py```### 2. Download a 10-K filing```bashpython src/download.py```Provide the requested company information such as ticker and CIK.### 3. Ingest the filing```bashpython src/ingest.py```The filing is cleaned, divided into SEC sections, chunked, and stored in SQLite.### 4. Build the FAISS index```bashpython src/build_index.py```### 5. Run the RAG system```bashpython src/rag.py```Example question:```textWhat cybersecurity risks does Microsoft discuss?```---## EvaluationThe project includes a multi-company evaluation dataset covering NVIDIA, AMD, and Microsoft.The evaluation code is used to analyze retrieval behavior across different companies and SEC sections.Metrics and experiments include section-level and company-level retrieval performance.The evaluation pipeline is still being expanded as the retrieval architecture evolves.---## Current LimitationsThe current implementation is intentionally kept relatively simple while retrieval strategies are evaluated.Current limitations include:- Company routing currently depends on known company names/tickers.- The LLM currently selects a single primary section before chunk retrieval.- Questions requiring evidence from multiple sections may require additional retrieval logic.- SEC HTML formatting differs between companies, so section parsing remains heuristic.- The current dataset contains a limited number of companies and filings.- No production web interface is included yet.---## Planned ImprovementsPossible next steps include:- adaptive multi-stage retrieval when the first section does not provide sufficient evidence;- evidence sufficiency evaluation before answer generation;- conditional retrieval across additional sections;- improved company routing;- larger multi-company evaluation datasets;- additional SEC filing types and filing years;- retrieval latency and token-cost evaluation;- user interface for interactive filing analysis.---## Tech Stack```textPythonSQLiteFAISSSentence TransformersCross-EncoderLangChainGroqBeautifulSoupSEC EDGAR```---## GoalThe goal of
