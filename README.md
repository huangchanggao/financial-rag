\# Financial RAG AssistantA Retrieval-Augmented Generation (RAG) system for analyzing SEC 10-K filings.一個用於分析 SEC 10-K 財報文件的 Retrieval-Augmented Generation（RAG）系統。This project builds an end-to-end financial document question-answering pipeline using SEC filings, structured metadata, vector retrieval, section-aware routing, and grounded LLM generation.本專案建立一套端到端的金融文件問答流程，使用 SEC 公開財報、結構化 metadata、向量檢索、Section-aware routing，以及具有來源依據的 LLM 回答。The goal is not only to build a working RAG system, but also to evaluate and improve retrieval quality using measurable metrics.本專案除了實作可運作的 RAG 系統，也建立 evaluation pipeline，透過量化指標分析並改善 Retrieval 品質。\---\## Overview / 專案概述Financial reports such as SEC 10-K filings are long, semi-structured documents containing business descriptions, risk factors, financial performance, market risks, corporate governance information, and other disclosures.SEC 10-K 財報是一種篇幅長、具有半結構化特性的文件，其中包含公司業務、風險因素、財務表現、市場風險、公司治理等資訊。A standard vector search approach may retrieve semantically related chunks from the wrong section of the filing.一般的 Vector Search 雖然可以找到語意相近的 chunks，但有可能從錯誤的財報章節取得內容。For example, a question about market risk may retrieve content from:例如使用者詢問 market risk 時，單純的 semantic search 可能取得：\- Item 1A - Risk Factors\- Item 5 - Market for Registrant's Common Equity\- Item 15 - Exhibits and Financial Statement Schedulesinstead of the more relevant:而不是更相關的：\- Item 7A - Quantitative and Qualitative Disclosures about Market RiskThis project introduces section-aware retrieval to improve retrieval precision by first predicting the relevant SEC section and then applying metadata filtering before vector search.因此，本專案加入 Section-aware Retrieval。系統會先根據使用者問題預測可能相關的 SEC Item，再利用 metadata filtering 限制搜尋範圍，最後執行向量檢索。\---\## Key Features / 核心功能\- Automatically downloads public SEC 10-K large amounts of HTML and Inline XBRL metadata.SEC 原始文件除了可閱讀內容，也包含大量 HTML 與 Inline XBRL metadata。Examples of XBRL-related tags include:常見的 XBRL tags 包括：\- ix:header\- ix:nonfraction\- ix:nonnumeric\- ix:continuation\- xbrli:context\- xbrli:entity\- xbrli:periodThe cleaning pipeline removes hidden XBRL metadata while preserving visible financial text.Cleaning pipeline 會刪除隱藏的 XBRL metadata，同時保留真正呈現在財報中的文字內容。Visible Inline XBRL tags are unwrapped so the underlying text remains available for retrieval.對於包含實際財務資訊的 Inline XBRL tag，系統只移除 tag 本身並保留內部文字，避免重要資訊遺失。\---\## Section-Aware Chunking / 依財報章節進行 ChunkingInstead of chunking the entire filing as one continuous document, the system first identifies SEC Item sections.系統不是直接把整份 10-K 當成一大段文字切 chunks，而是先辨識 SEC Item section。Examples include:例如：\- Item 1 - Business\- Item 1A - Risk Factors\- Item 7 - Management's Discussion and Analysis of Financial Condition and Results of Operations\- Item 7A - Quantitative and Qualitative Disclosures about Market Risk\- Item 9A - Controls and Procedures\- Item 10 - Directors, Executive Officers and Corporate Governance\- Item 11 - Executive CompensationSEC filings often contain Item headings both in the table of contents and in the actual document body.SEC 文件中的 Item heading 通常會同時出現在目錄與真正正文中。The ingestion pipeline identifies the actual body headings and splits the filing into sections before chunking.因此 ingestion pipeline 會辨識真正的正文 Item heading，先切 section，再對各 section 進行 chunking。Each chunk contains metadata such as:每個 chunk 都會保存：\- company\- ticker\- filing type\- filing date\- source file\- SEC section\- chunk index\- chunk IDThis metadata is later used for source attribution and section-aware retrieval.這些 metadata 後續可用於 citation 與 Section-aware Retrieval。\---\## Database Design / 資料庫設計SQLite is used to store structured document metadata.本專案使用 SQLite 儲存文件與 chunk metadata。The database contains three main tables:資料庫主要包含三張表：\### companiesStores company-level information.儲存公司層級資訊。Example fields / 欄位：\- id\- ticker\- company\_name\- cik\### filingsStores filing-level information.儲存每份 SEC Filing 的資訊。Example fields / 欄位：\- id\- company\_id\- form\_type\- filing\_date\- source\_file\### chunksStores text chunks.儲存切分後的文字 chunks。Example fields / 欄位：\- id\- filing\_id\- section\- chunk\_index\- chunk\_textForeign keys preserve relationships between companies, filings, and chunks.透過 Foreign Key 維持 company、filing 與 chunk 之間的關聯。Relationship / 關聯：Company&#x20;   |&#x20;   vFiling&#x20;   |&#x20;   vChunk\---\## Vector Retrieval / 向量檢索Each chunk is converted into an embedding using:每個 chunk 使用以下模型轉換成 embedding：sentence-transformers/all-MiniLM-L6-v2The vectors are stored in a FAISS index.產生的 vectors 儲存在 FAISS index 中。Each FAISS document also contains metadata copied from SQLite.每個 FAISS Document 同時保留 SQLite 中的重要 metadata。Example:{&#x20;   "chunk\_id": 308,&#x20;   "chunk\_index": 307,&#x20;   "section": "Item 7A - Quantitative and Qualitative Disclosures about Market Risk",&#x20;   "ticker": "NVDA",&#x20;   "company": "NVIDIA Corporation",&#x20;   "form\_type": "10-K",&#x20;   "filing\_date": "2026-02-25",&#x20;   "source\_file": "NVDA\_2026-02-25\_10K.html"}\---\## Baseline Retriever / 基準 RetrieverThe baseline retriever performs semantic similarity search across all chunks.Baseline Retriever 直接針對所有 chunks 進行 semantic similarity search。Example question:What market risks does NVIDIA discuss?Without section filtering, FAISS may retrieve chunks from:在沒有 section filtering 的情況下，FAISS 可能會取得：\- Item 1A - Risk Factors\- Item 5 - Market for Registrant's Common Equity\- Item 15 - Exhibits and Financial Statement SchedulesThis happens because different sections may contain semantically similar vocabulary.原因是不同 SEC Item 可能包含語意相似的文字。As a result, the correct section may not appear as the first retrieval result.因此即使正確文件存在，Retriever 也可能無法把它排在第一名。\---\## Section-Aware Retrieval / Section-aware 檢索To improve retrieval quality, the project introduces a section router.為改善 Retrieval 品質，本專案加入 Section Router。The router predicts the most relevant SEC Item based on the user's question.Router 會根據使用者問題判斷最可能相關的 SEC Item。Example:Question:What market risks does NVIDIA discuss?Predicted Section:Item 7A - Quantitative and Qualitative Disclosures about Market RiskThe retriever then applies metadata filtering before returning Top-k results.Retriever 會先根據預測出的 section 進行 metadata filtering，再從該 section 找出最相關的 Top-k chunks。Flow / 流程：Question&#x20;   |&#x20;   vroute\_section()&#x20;   |&#x20;   vItem 7A&#x20;   |&#x20;   vMetadata Filtering&#x20;   |&#x20;   vFAISS Similarity Search&#x20;   |&#x20;   vTop-k Item 7A ChunksIf the router cannot confidently determine a section, the system falls back to normal semantic retrieval.如果 Router 無法判斷應該使用哪個 section，系統會 fallback 回一般 semantic search。\---\## Example Retrieval / Retrieval 範例Question:What market risks does NVIDIA discuss?Section Router:Item 7A - Quantitative and Qualitative Disclosures about Market RiskRetrieved content includes:Retrieval 結果包含：\- Investment and interest rate risk\- 投資與利率風險\- Foreign exchange rate risk\- 外匯風險\- Publicly-held equity security price volatility\- 公開交易股票價格波動風險\- Investment portfolio sensitivity\- 投資組合敏感度With section-aware retrieval, retrieved chunks are restricted to the relevant Item 7A section.加入 Section-aware Retrieval 後，Retriever 能優先取得 Item 7A 中真正與問題相關的內容。\---\## Grounded RAG Generation / 具有來源依據的 RAG 回答Retrieved chunks are passed to the LLM as context.Retriever 找到的 chunks 會作為 Context 提供給 LLM。The generation prompt instructs the model to:Prompt 會要求模型：\- Answer only from retrieved SEC context\- 只能根據 Retrieved SEC Context 回答\- Avoid inventing unsupported facts\- 不可補充 context 中沒有的事實\- Avoid inventing numbers\- 不可自行產生數字\- State when context is insufficient\- Context 不足時必須明確說明\- Include source citations\- 回答必須包含來源 citationExample citation format:\[NVDA 10-K, 2026-02-25, Item 1A - Risk Factors, Chunk 199]This allows generated answers to be traced back to specific filing sections and chunks.這讓使用者可以追溯每個回答所依據的 filing、section 與 chunk。\---\## Insufficient Context Handling / 資訊不足處理The system is designed to avoid answering questions that cannot be supported by the SEC filing.系統會避免回答財報 Context 無法支持的問題。Example:What was NVIDIA's stock price on August 1, 2026?If the retrieved filing context does not contain this information, the model is instructed not to guess.如果 SEC filing 中沒有相關資訊，LLM 會回覆 Context 不足，而不是自行猜測答案。This reduces unsupported generation and hallucination.這可以降低 unsupported claims 與 hallucination。\---\## Evaluation / 評估方法Retrieval quality is Section Router 採用 Rule-based 方法。It performs well when questions contain recognizable terms such as:當問題包含以下明確詞彙時，Router 通常能正確分類：\- market risk\- competition\- revenue\- internal controls\- corporate governance\- executive compensationHowever, unseen paraphrases may not match existing rules.但使用者如果使用不同的語意表達，keyword rules 可能無法判斷。Example:Where can investors find NVIDIA's disclosures concerning pay for senior management?A human can infer that this refers to executive compensation.人類可以理解「pay for senior management」代表 executive compensation。However, a keyword-based router may fail to map it to Item 11.但 Rule-based Router 如果沒有相關 keyword，就可能無法分類到 Item 11。In this case, the system falls back to baseline semantic retrieval.這種情況下系統會 fallback 回一般 FAISS Semantic Retrieval。This limitation is visible in the holdout evaluation and motivates future work on semantic or LLM-based section routing.這也是後續考慮加入 LLM-based Section Router 的主要原因。\---\## Why Section-Aware Retrieval? / 為什麼需要 Section-Aware Retrieval？Pure semantic retrieval can confuse sections containing overlapping vocabulary.純 semantic retrieval 可能因為不同 Section 使用相似文字而產生錯誤。For example:例如："market risk"may be semantically similar to content in:可能與以下內容都有一定語意相似度：\- general business risks\- stock market information\- financial exhibitsHowever, SEC filings have strong document structure.但是 SEC 10-K 本身具有非常明確的文件結構。Therefore, the system can use both semantic similarity and document structure.因此可以把文件結構也當作 retrieval signal。Baseline:Semantic SimilarityImproved:Semantic Similarity\+SEC Document StructureThis reduces retrieval noise and improves section-level precision.這可以減少 Retrieval Noise，並提高 Section-level Precision。\---\## Setup / 安裝方式Create and activate a Conda environment.建立並啟用 Conda Environment：conda create -n
