# Financial RAG AssistantA Retrieval-Augmented Generation (RAG) system for analyzing SEC 10-K filings with section-aware retrieval and grounded LLM generation.一個用於分析 SEC 10-K 財報文件的 Retrieval-Augmented Generation（RAG）系統，結合 Section-Aware Retrieval、FAISS Vector Search 與 Grounded LLM Generation。This project builds an end-to-end financial document question-answering pipeline using SEC filings, structured metadata, vector retrieval, section routing, metadata filtering, and grounded LLM generation.本專案建立一套端到端的金融文件問答流程，從 SEC Filing 下載與資料清理開始，經過 Section-Based Chunking、SQLite Metadata、FAISS Retrieval、Section Router，最後由 LLM 根據 Retrieved Context 產生具有來源依據的回答。The project also includes a retrieval evaluation pipeline to measure retrieval quality and compare a baseline semantic retriever with a section-aware retrieval pipeline.本專案同時建立 Retrieval Evaluation Pipeline，透過量化指標比較 Baseline Semantic Retrieval 與 Section-Aware Retrieval Pipeline 的差異。---## Overview / 專案概述SEC 10-K filings are long, semi-structured financial documents containing information such as:SEC 10-K 財報是篇幅長、具有半結構化特性的金融文件，其中包含：- Business descriptions / 公司業務- Risk factors / 風險因素- Financial performance / 財務表現- Market risks / 市場風險- Internal controls / 內部控制- Corporate governance / 公司治理- Executive compensation / 高階主管薪酬A standard vector search can retrieve semantically similar chunks from the wrong section of the filing.一般 Vector Search 雖然可以找到語意相似的文件片段，但可能從錯誤的 SEC Item 取得內容。For example, a question about market risk may retrieve content from:例如詢問 market risk 時，單純 Semantic Search 可能取得：- Item 1A - Risk Factors- Item 5 - Market for Registrant's Common Equity- Item 15 - Exhibits and Financial Statement Schedulesinstead of the more relevant:而不是更相關的：- Item 7A - Quantitative and Qualitative Disclosures about Market RiskTo address this problem, this project introduces a Section-Aware Retrieval pipeline.因此，本專案加入 Section-Aware Retrieval Pipeline：1. Predict the most relevant SEC Item for the query.2. Apply metadata filtering using the predicted section.3. Perform FAISS similarity search inside the filtered section.4. Pass the retrieved chunks to the LLM for grounded generation.也就是：1. 先判斷問題最可能屬於哪個 SEC Item。2. 使用預測出的 Section 進行 Metadata Filtering。3. 在篩選後的 Section 中執行 FAISS Similarity Search。4. 將 Retrieved Chunks 提供給 LLM 產生回答。---## Key Features / 核心功能- Automatically downloads public SEC 10-K filings    自動下載 SEC 公開 10-K 財報- Cleans SEC HTML and Inline XBRL content    清理 SEC HTML 與 Inline XBRL amounts of HTML and Inline XBRL metadata.SEC 原始文件除了真正可閱讀的財報內容，也包含大量 HTML 與 Inline XBRL Metadata。Examples include:- ix:header- ix:nonfraction- ix:nonnumeric- ix:continuation- xbrli:context- xbrli:entity- xbrli:periodThe cleaning pipeline removes hidden XBRL metadata while preserving visible financial text.Cleaning Pipeline 會移除隱藏的 XBRL Metadata，同時保留真正顯示在財報中的文字。Visible Inline XBRL tags are unwrapped instead of deleting their text content.對於包含實際資訊的 Inline XBRL Tags，系統只移除 Tag 本身並保留內部文字，避免重要財務內容被刪除。---## Section-Aware Chunking / Section-Aware ChunkingInstead of chunking the entire filing as one continuous document, the system first identifies SEC Item sections.系統不是直接把整份 10-K 當成一大段文字切成 Chunks，而是先辨識 SEC Item。Examples include:- Item 1 - Business- Item 1A - Risk Factors- Item 7 - Management's Discussion and Analysis of Financial Condition and Results of Operations- Item 7A - Quantitative and Qualitative Disclosures about Market Risk- Item 9A - Controls and Procedures- Item 10 - Directors, Executive Officers and Corporate Governance- Item 11 - Executive CompensationSEC filings may contain Item headings both in the table of contents and the actual document body.SEC Filing 中的 Item Heading 可能同時出現在目錄與真正正文中。The ingestion pipeline identifies the actual body sections first and then performs chunking within each section.因此，系統會先辨識真正正文的 Item Section，再在各 Section 內進行 Chunking。Each chunk contains metadata such as:- company- ticker- filing type- filing date- source file- SEC section- chunk index- chunk IDThese metadata fields are later used for retrieval filtering and source attribution.這些 Metadata 後續會用於 Section-Aware Retrieval 與 Citation。---## Database Design / 資料庫設計SQLite is used to store structured document metadata.本專案使用 SQLite 儲存結構化的 Company、Filing 與 Chunk Metadata。The database contains three main tables.### companiesStores company-level information.儲存公司層級資訊。Example fields:- id- ticker- company_name- cik### filingsStores SEC filing information.儲存 SEC Filing 資訊。Example fields:- id- company_id- form_type- filing_date- source_file### chunksStores document chunks.儲存切分後的文件 Chunks。Example fields:- id- filing_id- section- chunk_index- chunk_textForeign keys preserve relationships between companies, filings, and chunks.透過 Foreign Key 維持 Company、Filing 與 Chunk 之間的關聯。Company↓Filing↓Chunk---## Vector Retrieval / 向量檢索Each chunk is converted into an embedding using:sentence-transformers/all-MiniLM-L6-v2The vectors are stored in a FAISS index.每個 Chunk 會轉換為 Embedding，並儲存在 FAISS Vector Index 中。Each FAISS Document also contains metadata copied from SQLite.每個 FAISS Document 同時保留重要 Metadata。Example:{    "chunk_id": 308,    "chunk_index": 307,    "section": "Item 7A - Quantitative and Qualitative Disclosures about Market Risk",    "ticker": "NVDA",    "company": "NVIDIA Corporation",    "form_type": "10-K",    "filing_date": "2026-02-25",    "source_file": "NVDA_2026-02-25_10K.html"}---## Baseline Retriever / 基準 RetrieverThe baseline retriever performs semantic similarity search across all chunks.Baseline Retriever 直接針對全部 Chunks 執行 Semantic Similarity Search。Example:What market risks does NVIDIA discuss?Without section filtering, FAISS may retrieve chunks from:- Item 1A - Risk Factors- Item 5 - Market for Registrant's Common Equity- Item 15 - Exhibits and Financial Statement SchedulesThis happens because different sections may contain semantically overlapping vocabulary.這是因為不同 SEC Section 可能包含相似的金融詞彙，使向量檢索找到「語意相關，但文件位置錯誤」的結果。As a result, the most relevant SEC section may not appear at Rank 1.因此正確 Section 不一定會出現在第一筆 Retrieval Result。---## Section-Aware Retrieval / Section-Aware 檢索To improve retrieval quality, the project introduces a rule-based section router.為改善 Retrieval 品質，本專案加入 Rule-Based Section Router。The router predicts the most relevant SEC Item based on the user's question.Router 會先根據使用者問題判斷最可能相關的 SEC Item。Example:### QuestionWhat market risks does NVIDIA discuss?### Predicted SectionItem 7A - Quantitative and Qualitative Disclosures about Market RiskThe predicted section is then used as a metadata filter during FAISS retrieval.預測出的 Section 會作為 FAISS Retrieval 的 Metadata Filter。Flow:Question↓route_section()↓Predicted SEC Item↓Metadata Filtering↓FAISS Similarity Search↓Top-k ChunksIf the router cannot determine a section, the system falls back to normal semantic retrieval across the entire vector store.如果 Router 無法判斷 Section，系統會 fallback 到一般全域 FAISS Semantic Search。---## End-to-End RAG Integration / RAG 整合Section-aware retrieval is integrated directly into the RAG generation pipeline.Section-Aware Retrieval 不只用於獨立 Retriever 或 Evaluation，也已實際整合進 RAG 問答流程。The full runtime flow is:User Question↓Section Router↓Metadata-Filtered FAISS Retrieval↓Top-k Context↓Groq LLM↓Grounded Answer↓SEC Section + Chunk CitationsFor example, the query:What market risks does NVIDIA discuss?is routed to:Item 7A - Quantitative and Qualitative Disclosures about Market Riskand the retrieved context contains topics such as:- Interest-rate risk- Foreign-exchange rate risk- Equity-security market-price volatility- Investment portfolio sensitivity這可以避免原本 Baseline Retriever 將問題導向 Item 1A 的一般風險內容。---## Grounded RAG Generation / Grounded RAG 回答Retrieved chunks are passed to the LLM as context.Retriever 找到的 Chunks 會作為 Context 提供給 LLM。The generation prompt instructs the model to:- Answer only from retrieved SEC context- 只能根據 Retrieved SEC Context 回答- Avoid inventing unsupported facts- 不可補充 Context 中沒有的事實- Avoid inventing unsupported numbers- 不可自行產生無來源數字- State when context is insufficient- Context 不足時必須明確說明- Include source citations- 回答必須包含來源 CitationExample citation:[NVDA 10-K, 2026-02-25, Item 7A, Chunk 308]This allows generated answers to be traced back to specific filing sections and chunks.這讓回答可以追溯到特定 Filing、Section 與 Chunk。---## Insufficient Context Handling / 資訊不足處理The system avoids answering questions that cannot be supported by the SEC filing.系統會避免回答 SEC Context 無法支持的問題。Example:What was NVIDIA's stock price on August 1, 2026?If the filing context does not contain this information, the model is instructed not to guess.如果 Retrieved Filing Context 中沒有這項資訊，LLM 會回覆 Context 不足，而不是自行猜測。This reduces unsupported claims and hallucination.這可以降低 Unsupported Claims 與 Hallucination。---## Evaluation / 評估方法Retrieval quality is evaluated using manually labeled datasets.本專案使用人工標註 Dataset 評估 Retrieval Pipeline。Each evaluation item contains:- question- expected_section- expected_keywordsExample:{    "question": "What market risks does NVIDIA discuss?",    "expected_section": "Item 7A - Quantitative and Qualitative Disclosures about Market Risk",    "expected_keywords": [        "market risk",        "interest",        "foreign"    ]}---## Evaluation Metrics / 評估指標The evaluation includes:- Section-Level Retrieval Hit@1- Section-Level Retrieval Hit@3- Section-Level Retrieval Hit@5- Keyword Recall@5### Section-Level Retrieval Hit@1Checks whether the expected SEC section appears in the first retrieved result.檢查第一筆 Retrieved Result 是否來自 Expected SEC Section。### Section-Level Retrieval Hit@3Checks whether the expected SEC section appears within the Top-3 retrieved results.檢查 Top-3 Results 是否包含 Expected Section。### Section-Level Retrieval Hit@5Checks whether the expected SEC section appears within the Top-5 retrieved results.檢查 Top-5 Results 是否包含 Expected Section。### Keyword Recall@5Checks whether manually labeled expected keywords appear in the combined Top-5 retrieved context.檢查 Top-5 Retrieved Context 是否涵蓋人工標註的重要關鍵資訊。---## Important Evaluation Note / Evaluation 指標說明The baseline retriever performs FAISS similarity search across all document chunks.Baseline Retriever 直接在全部文件 Chunks 中執行 FAISS Similarity Search。The section-aware pipeline first predicts an SEC section and then performs FAISS retrieval within that metadata-filtered section.Section-Aware Pipeline 則會先進行 Section Routing，再於預測出的 Section 中執行 Filtered FAISS Retrieval。Therefore, the reported Section-Aware Hit@k metrics reflect the combined effect of:因此，Section-Aware Hit@k 反映的是整體 Pipeline 效果，包括：- Section routing- Metadata filtering- FAISS retrievalThey should not be interpreted as isolated FAISS ranking performance.因此這些數字不應解讀為「單獨 FAISS Retriever 的 Ranking 表現」，而是 Routing + Filtering + Retrieval 的整體 Section-Level Retrieval Performance。---## Development Set Results / Development Set 結果The original 20-question evaluation dataset was used to analyze retrieval failures and refine the such as:- market risk- competition- revenue- internal controls- corporate governance- executive compensationHowever, unseen paraphrases may not match existing routing rules.但如果使用者採用不同的語意表達方式，Keyword Rules 可能無法正確分類。Example:Where can investors find NVIDIA's disclosures concerning pay for senior management?A human can infer that this refers to executive compensation.人類可以理解 pay for senior management 指的是 Executive Compensation。However, the current rule-based router may fail to map it to Item 11.但目前 Rule-Based Router 可能無法把這句話分類到 Item 11。If routing fails, the system falls back to baseline semantic retrieval.Router 無法判斷時，系統會 fallback 到一般 Semantic Retrieval。This limitation motivates future work on semantic or LLM-based section routing.這也是未來考慮使用 LLM-Based Section Router 的主要原因。---## Why Section-Aware Retrieval? / 為什麼使用 Section-Aware Retrieval？Pure semantic retrieval mainly relies on vector similarity.純 Semantic Retrieval 主要依賴 Vector Similarity。However, SEC filings already contain strong structural information.但是 SEC Filing 本身具有非常明確的文件結構。Therefore, document structure can be used as an additional retrieval signal.因此可以將 SEC Section 結構視為額外 Retrieval Signal。Baseline:Semantic SimilarityImproved:Section Routing+Metadata Filtering+Semantic SimilarityThis reduces retrieval noise and improves section-level ranking.這可以減少 Retrieval Noise，並改善正確 Section 在 Retrieval Results 中的 Ranking。---## Setup / 安裝方式Create a Conda environment:conda create -n financial-rag
