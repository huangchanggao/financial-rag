# Financial RAG — SEC 10-K Analysis SystemA multi-company Retrieval-Augmented Generation (RAG) system for analyzing SEC 10-K filings.使用多公司 SEC 10-K 財報建立的 Retrieval-Augmented Generation（RAG）系統，結合結構化文件解析、LLM Section Selection、FAISS Retrieval 與 Cross-Encoder Reranking，讓模型根據實際財報內容回答問題。---## Overview｜專案概述Large SEC 10-K filings contain many sections and hundreds of text chunks. Searching the entire document directly with vector similarity may retrieve semantically similar but contextually incorrect content.SEC 10-K 文件篇幅很長，包含多個不同 Item 與大量文字 chunks。若直接對整份文件進行向量搜尋，容易抓到「文字看起來相似，但實際用途不同」的內容。This project therefore uses a structured retrieval pipeline:本專案因此採用分層式的 retrieval 流程：1. Identify the company from the user's question.     從問題中辨識公司。2. Load the company's SEC 10-K section metadata from SQLite.     從 SQLite 取得該公司的所有 10-K section metadata。3. Use an LLM to select the section most likely to contain the answer.     使用 LLM 判斷最可能包含答案的 section。4. Perform FAISS retrieval only inside the selected company and section.     僅在指定公司與 section 中使用 FAISS 搜尋相關 chunks。5. Rerank retrieved chunks using a Cross-Encoder.     使用 Cross-Encoder 對候選 chunks 重新排序。6. Send the highest-ranked evidence to the LLM for grounded answer generation.     將最相關的 evidence 提供給 LLM，產生有來源依據的回答。Current companies:目前已加入：- NVIDIA (`NVDA`)- Advanced Micro Devices (`AMD`)- Microsoft (`MSFT`)---## Architecture｜系統架構```textUser Question使用者問題      |      vCompany / Ticker Router公司辨識      |      vSQLite Section Metadata取得該公司的 Section Metadata      |      vLLM Section SelectorLLM 選擇最相關 Section      |      vSelected SEC 10-K Section選定的 10-K Section      |      vFAISS Chunk RetrievalFAISS 搜尋候選 Chunks      |      vCross-Encoder RerankingCross-Encoder 重新排序      |      vTop-K Evidence      |      vGrounded LLM Answer有來源依據的回答```### Example｜範例Question:```textWhat market risks does AMD discuss?```Possible retrieval flow:可能的 retrieval 流程：```textAMD ↓Item 7A ↓FAISS candidate retrieval ↓Cross-Encoder reranking ↓Top 5 evidence chunks ↓Grounded answer```---## Features｜主要功能### 1. Multi-company SEC Ingestion｜多公司 SEC 財報處理The ingestion pipeline supports multiple companies and stores company, filing, and chunk metadata in SQLite.資料處理流程支援多家公司，並使用 SQLite 管理公司、財報與 chunk metadata。Current companies:```textNVDAAMDMSFT```---### 2. SEC 10-K Section Parsing｜10-K Section 解析The parser detects standard SEC 10-K sections such as:Parser 會辨識標準 10-K Item，例如：```textItem 1Item 1AItem 1BItem 1CItem 2Item 7Item 7AItem 8...Item 16```Section identifiers and titles are stored separately.Section 編號與標題會分開保存，例如：```textsection: Item 1Atitle: RISK FACTORS```This makes the section identifier stable while preserving semantic information from the original filing title.這樣可以保留穩定的 section metadata，同時保存原始標題中的語意資訊。---### 3. Section-aware Chunking｜依 Section 切分 ChunksEach extracted section is split into overlapping chunks while preserving metadata.每個 section 會再切成具有 overlap 的文字 chunks，同時保留：```texttickerfiling datesectionsection titlechunk index```Current text splitting settings:目前 chunking 設定：```textchunk size: 1000chunk overlap: 150```---### 4. SQLite Metadata Storage｜SQLite 資料管理The project uses three main tables:專案主要使用三張資料表：```textcompaniesfilingschunks```Relationships:資料關係：```textCompany  ↓Filing  ↓Chunks```This avoids duplicating company and filing metadata across every chunk.這樣可以避免每個 chunk 重複保存完整的公司與財報資料。---### 5. LLM Section Selection｜LLM Section 選擇Instead of immediately searching every chunk in the database, the system first provides the available SEC sections of the detected company to an LLM.系統不會一開始就直接搜尋所有 chunks，而是先將該公司的所有 SEC section metadata 提供給 LLM。Example:```textQuestion:What are AMD's main risk factors?LLM selected section:Item 1A```The selected section then becomes a metadata filter for the chunk retrieval stage.選出的 section 會作為後續 chunk retrieval 的 metadata filter。---### 6. FAISS Retrieval｜FAISS 向量檢索After section selection, FAISS performs semantic retrieval only inside:完成 section selection 後，FAISS 只會在以下範圍搜尋：```textselected company+selected section```Embedding model:```textsentence-transformers/all-MiniLM-L6-v2```FAISS is used mainly as a candidate-generation stage rather than the final relevance decision.FAISS 的主要用途是快速找出候選 chunks，而不是直接決定最後的 evidence。---### 7. Cross-Encoder Reranking｜Cross-Encoder 重新排序Retrieved FAISS candidates are reranked using:FAISS 找出的候選 chunks 會再使用：```textcross-encoder/ms-marco-MiniLM-L-6-v2```The Cross-Encoder evaluates the question and chunk together, allowing a more detailed relevance comparison than embedding distance alone.Cross-Encoder 會同時讀取：```textQuestion + Chunk```因此可以比單純 embedding distance 更細緻地判斷內容是否真正與問題相關。---### 8. Grounded Answer Generation｜有依據的回答生成The final LLM is instructed to answer only from retrieved SEC filing evidence.最終回答模型只能根據 retrieval 找到的 SEC filing context 回答。Rules include:規則包括：- Do not use outside knowledge.    不使用外部知識補充答案。- Do not invent facts or financial numbers.    不自行生成財務數據或事實。- State when the retrieved evidence is insufficient.    若證據不足，需要明確說明。- Cite the retrieved SEC sources.    回答需引用 retrieval 找到的來源。Current answer model:```textopenai/gpt-oss-20b```via Groq.---## Data Pipeline｜資料處理流程```textSEC EDGAR    |    vDownload 10-K HTML下載 10-K    | system still has several limitations:目前系統仍有以下限制：- Company routing currently depends on known company names and tickers.    公司辨識目前主要依賴已知的公司名稱與 ticker。- The LLM currently selects only one primary section.    LLM 目前只會先選一個主要 section。- Some questions may require evidence from multiple sections.    部分問題可能需要跨多個 section 才能完整回答。- SEC HTML structure differs between companies.    不同公司的 SEC HTML 結構存在差異。- Section parsing is still heuristic.    Section parser 目前仍包含 heuristic 方法。- The current dataset contains only a limited number of companies and filings.    目前資料集仍只有少量公司與 filings。- No production web interface is included yet.    尚未建立正式 Web UI。---## Planned Improvements｜後續方向Possible next steps include:接下來可能加入：- Adaptive multi-stage retrieval when the first section is
