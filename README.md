# Financial RAG AssistantA Retrieval-Augmented Generation (RAG) system for analyzing SEC 10-K filings.一個用於分析 SEC 10-K 財報文件的 Retrieval-Augmented Generation（RAG）系統。This project builds an end-to-end financial document question-answering pipeline using SEC filings, structured metadata, vector retrieval, section-aware routing, and grounded LLM generation.本專案建立一套端到端的金融文件問答流程，使用 SEC 公開財報、結構化 metadata、向量檢索、Section-aware Routing，以及具有來源依據的 LLM 回答。The goal is not only to build a working RAG system, but also to evaluate and improve retrieval quality using measurable metrics.本專案除了實作可運作的 RAG 系統，也建立 evaluation pipeline，透過量化指標分析並改善 Retrieval 品質。---## Overview / 專案概述SEC 10-K filings are long, semi-structured financial documents containing information such as:SEC 10-K 財報是篇幅長、具有半結構化特性的文件，包含：- Business descriptions / 公司業務- Risk factors / 風險因素- Financial performance / 財務表現- Market risks / 市場風險- Corporate governance / 公司治理- Executive compensation / 高階主管薪酬A standard vector search may retrieve semantically similar chunks from the wrong section of the filing.一般的 Vector Search 雖然可以找到語意相近的 chunks，但可能從錯誤的財報章節取得內容。For example, a question about market risk may retrieve content from:例如詢問 market risk 時，單純的 Semantic Search 可能取得：- Item 1A - Risk Factors- Item 5 - Market for Registrant's Common Equity- Item 15 - Exhibits and Financial Statement Schedulesinstead of the more relevant:而不是更相關的：- Item 7A - Quantitative and Qualitative Disclosures about Market RiskTo address this problem, this project introduces Section-Aware Retrieval.因此，本專案加入 Section-Aware Retrieval，先預測問題最相關的 SEC Item，再利用 metadata filtering 限制搜尋範圍。---## Key Features / 核心功能- Automatically downloads public SEC 10-K filings    自動下載 SEC 公開 10-K 財報- Cleans SEC HTML and Inline XBRL content    清理 SEC HTML 與 Inline XBRL 內容- Removes hidden XBRL metadata while preserving visible financial text    移除隱藏 XBRL metadata，同時保留實際財報文字- Detects SEC Item sections before chunking    在 Chunking 前先辨識 SEC Item Section- Performs section-based chunking    依財報 Section 進行 Chunking- Stores structured metadata in SQLite    使用 SQLite 管理結構化 Metadata- Generates embeddings using HuggingFace Sentence Transformers    使用 HuggingFace Sentence Transformers 建立 Embeddings- Builds a FAISS vector index    使用 FAISS 建立 Vector Index- Supports semantic Top-k retrieval    支援 Semantic Top-k Retrieval- Implements a rule-based section router    實作 Rule-based Section Router- Applies SEC Item-level metadata filtering    根據 SEC Item Metadata 過濾 Retrieval 範圍- Generates grounded answers using Groq LLM    使用 Groq LLM 根據 Retrieved Context 產生回答- Provides source citations with SEC section and chunk ID    回答附帶 SEC Section 與 Chunk ID Citation- Refuses unsupported questions when context is insufficient    Context 不足時避免產生無根據答案- Includes retrieval evaluation with Hit@1, Hit@3, Hit@5 and Keyword Recall    使用 Hit@1、Hit@3、Hit@5 Source / 資料來源The project currently uses public NVIDIA SEC 10-K filing data.目前專案使用 NVIDIA 公開 SEC 10-K 財報作為主要資料來源。### CompanyNVIDIA Corporation### TickerNVDA### CIK0001045810### contain large amounts of HTML and Inline XBRL metadata.SEC 原始文件除了可閱讀內容，也包含大量 HTML 與 Inline XBRL metadata。Examples include:- ix:header- ix:nonfraction- ix:nonnumeric- ix:continuation- xbrli:context- xbrli:entity- xbrli:periodThe cleaning pipeline removes hidden XBRL metadata while preserving visible financial text.Cleaning Pipeline 會刪除隱藏的 XBRL metadata，同時保留真正呈現在財報中的文字。Visible Inline XBRL tags are unwrapped instead of deleting their text content.對於包含實際財務資訊的 Inline XBRL tag，系統只移除 tag 本身，保留內部文字，避免重要資訊遺失。---## Section-Aware Chunking / Section-Aware ChunkingInstead of chunking the entire filing as one continuous document, the system first identifies SEC Item sections.系統不是直接把整份 10-K 當成一大段文字切成 chunks，而是先辨識 SEC Item。Examples:- Item 1 - Business- Item 1A - Risk Factors- Item 7 - Management's Discussion and Analysis of Financial Condition and Results of Operations- Item 7A - Quantitative and Qualitative Disclosures about Market Risk- Item 9A - Controls and Procedures- Item 10 - Directors, Executive Officers and Corporate Governance- Item 11 - Executive CompensationSEC filings may contain Item headings both in the table of contents and the actual document body.SEC 文件中的 Item Heading 可能同時出現在目錄和真正正文。The ingestion pipeline identifies the actual body sections first and then performs chunking within each section.因此系統會先辨識正文 Section，再在各 Section 內進行 Chunking。Each chunk contains metadata such as:- company- ticker- filing type- filing date- source file- SEC section- chunk index- chunk IDThese metadata fields are later used for retrieval filtering and source attribution.這些 Metadata 後續用於 Section-Aware Retrieval 與 Citation。---## Database Design / 資料庫設計SQLite is used to store structured document metadata.本專案使用 SQLite 儲存文件與 Chunk Metadata。The database contains three main tables.### companiesStores company-level information.儲存公司層級資訊。Example fields:- id- ticker- company_name- cik### filingsStores SEC filing information.儲存每份 SEC Filing 的資訊。Example fields:- id- company_id- form_type- filing_date- source_file### chunksStores text chunks.儲存切分後的文件 Chunks。Example fields:- id- filing_id- section- chunk_index- chunk_textForeign keys preserve relationships between companies, filings, and chunks.透過 Foreign Key 維持 Company、Filing 與 Chunk 的關聯。Company↓Filing↓Chunk---## Vector Retrieval / 向量檢索Each chunk is converted into an embedding using:sentence-transformers/all-MiniLM-L6-v2The vectors are stored in a FAISS index.每個 Chunk 會轉換為 Embedding，並儲存在 FAISS Index 中。Each FAISS Document also contains metadata copied from SQLite.Example metadata:{    "chunk_id": 308,    "chunk_index": 307,    "section": "Item 7A - Quantitative and Qualitative Disclosures about Market Risk",    "ticker": "NVDA",    "company": "NVIDIA Corporation",    "form_type": "10-K",    "filing_date": "2026-02-25",    "source_file": "NVDA_2026-02-25_10K.html"}---## Baseline Retriever / 基準 RetrieverThe baseline retriever performs semantic similarity search across all document chunks.Baseline Retriever 直接針對所有 Chunks 執行 Semantic Similarity Search。Example question:What market risks does NVIDIA discuss?Without section filtering, FAISS may retrieve chunks from:- Item 1A- Item 5- Item 15Different sections may contain semantically similar vocabulary, causing retrieval noise.不同 Section 可能包含相似詞彙，因此 Semantic Search 可能找到內容相關、但 Section 錯誤的文件。---## Section-Aware Retrieval / Section-Aware 檢索To improve retrieval quality, the project introduces a section router.為改善 Retrieval 品質，本專案加入 Section Router。Example:Question:What market risks does NVIDIA discuss?Predicted Section:Item 7A - Quantitative and Qualitative Disclosures about Market RiskThe retriever applies metadata filtering before returning Top-k results.Retriever 會根據預測出的 Section 進行 Metadata Filtering，再從該 Section 找出最相關的 Top-k Chunks。Question↓route_section()↓Predicted SEC Item↓Metadata Filtering↓FAISS Similarity Search↓Top-k ChunksIf the router cannot determine a section, the system falls back to normal semantic retrieval.如果 Router 無法判斷 Section，系統會 fallback 到一般 FAISS Semantic Search。---## Example Retrieval / Retrieval 範例### QuestionWhat market risks does NVIDIA discuss?### Predicted SectionItem 7A - Quantitative and Qualitative Disclosures about Market Risk### Retrieved Topics- Investment and interest rate risk- Foreign exchange rate risk- Equity security price volatility- Investment portfolio sensitivity加入 Section-Aware Retrieval 後，Top-k 結果能集中在真正相關的 Item 7A。---## Grounded RAG Generation / Grounded RAG 回答Retrieved chunks are passed to the LLM as context.Retriever 找到的 Chunks 會作為 Context 提供給 LLM。The prompt instructs the model to:- Answer only from retrieved SEC context- 不可補充 Context 中沒有的事實- Avoid inventing unsupported numbers- 不可自行產生無來源數字- State when context is insufficient- Context 不足時必須明確說明- Include source citations- 回答附帶來源 CitationExample citation:[NVDA 10-K, 2026-02-25, Item 1A - Risk Factors, Chunk 199]This allows answers to be traced back to specific filing sections and chunks.這讓回答可以追溯到特定 Filing、Section 與 Chunk。---## Insufficient Context Handling / 資訊不足處理The system avoids answering questions that cannot be supported by the SEC filing.系統會避免回答 SEC Context 無法支持的問題。Example:What was NVIDIA's stock price on August 1, 2026?If the filing does not contain this information, the model is instructed not to guess.如果 Filing Context 沒有這項資訊，LLM 會回覆資訊不足，而不是自行猜測答案。---## Evaluation / 評估方法Retrieval quality is evaluated using manually labeled datasets.本專案使用人工標註 Dataset 評估 Retrieval 品質。Each evaluation item contains:- question- expected_section- expected_keywordsExample:{    "question": "What market risks does NVIDIA discuss?",    "expected_section": "Item 7A - Quantitative and Qualitative Disclosures about Market Risk",    "expected_keywords": [        "market risk",        "interest",        "foreign"    ]}Evaluation metrics include:- Section Hit@1- Section Hit@3- Section Hit@5- Keyword Recall@5### Hit@1Checks whether the first retrieved chunk comes from the expected section.檢查第一個 Retrieved Chunk 是否來自正確 Section。### Hit@3Checks whether the expected section appears within the Top-3 results.檢查 Top-3 是否包含正確 Section。### Hit@5Checks whether the expected section appears within the Top-5 results.檢查 Top-5 是否包含正確 Section。### Keyword Recall@5Checks whether expected keywords appear in the combined Top-5 context.檢查 Top-5 Retrieved Context 是否包含人工標註的重要資訊。---## Development Set Results / Development Set 結果### Baseline RetrieverHit@1: 55%Hit@3: 80%Hit@5: 85%### Section-Aware RetrieverHit@1: 100%Hit@3: 100%Hit@5: 100%The section router was adjusted based on errors observed in this dataset.由於這組 Dataset 的 Retrieval Failure 曾被用來改善 Router，因此這些結果被視為 Development Set Results，而不是最終泛化能力。---## Holdout Evaluation / Holdout 測試A separate 20-question holdout dataset was created after the router had been developed.在 Router 完成後，另外建立 20 題未參與原始規則設計的 Holdout Dataset。### Baseline RetrieverHit@1: 45%Hit@3: 85%Hit@5: 90%### Section-Aware RetrieverHit@1: 60%Hit@3: 90%Hit@5: 95%### Average Keyword Recall@583.33%---## Retrieval Improvement / Retrieval 改善結果### Hit@1Baseline: 45%Section-Aware: 60%Improvement: +15 percentage points提升 15 個百分點。### Hit@3Baseline: 85%Section-Aware: 90%Improvement: +5 percentage points提升 5 個百分點。### Hit@5Baseline: 90%Section-Aware: 95%Improvement: +5 percentage points提升 5 個百分點。The largest improvement appears at Hit@1.最大的改善出現在 Hit@1，表示 Section-Aware Filtering 能提高第一筆 Retrieval Result 就命中正確 Section 的機率。---## Development vs Holdout / Development 與 Holdout### Development SetBaseline Hit@1: 55%Section-Aware Hit@1: 100%### Holdout SetBaseline Hit@1: 45%Section-Aware Hit@1: 60%The development dataset was used to analyze retrieval failures and refine the routing rules.Development Dataset 用於分析 Retrieval Failure 與改善 Router。The holdout dataset was not used during the original router design.Holdout Dataset 則沒有參與原始 Router 規則設計。This separation prevents tuned development performance from being treated as true generalization performance.這樣可以避免把針對特定 Dataset 調整後的結果誤認為真正泛化能力。---## Observed Limitations / 目前限制The current section router is rule-based.目前 Section Router 採用 Rule-Based 方法。It performs well when questions contain recognizable expressions such as:- market risk- competition- revenue- internal controls- corporate governance- executive compensationHowever, unseen paraphrases may not match existing rules.但如果使用者使用不同的語意表達方式，目前規則可能無法分類。Example:Where can investors find NVIDIA's disclosures concerning pay for senior management?A human can infer that this refers to executive compensation, but the rule-based router may fail to map it to Item 11.人類可以理解 pay for senior management 指的是 Executive Compensation，但 Keyword-Based Router 不一定能判斷。This motivates future work on semantic or LLM-based section routing.因此後續預計加入 LLM-Based Section Router。---## Why Section-Aware Retrieval? / 為什麼使用 Section-Aware Retrieval？Pure semantic retrieval relies mainly on vector similarity.純 Semantic Retrieval 主要依賴 Vector Similarity。However, SEC filings already contain strong structural information.但是 SEC Filing 本身具有非常明確的文件結構。Therefore, the improved retriever combines:Semantic Similarity+SEC Document StructureThis reduces retrieval noise and improves section-level precision.將 Semantic Similarity 與 SEC 文件結構結合，可以減少 Retrieval Noise，並提高正確 Section 的 Ranking。---## Setup / 安裝方式Create a Conda environment:conda create
